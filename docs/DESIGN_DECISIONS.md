本文件记录评审意见中**经评估后不采纳**的条目及理由，避免后续重复评估；采纳项见对应实现与提交记录。

## 程序意见1：客户端预测与回滚（乐观更新）→ **不采纳**

**评审建议**：对玩家自己的操作（买牌、出牌）做客户端乐观更新 + 服务端拒绝时回滚；引入"状态快照/事件溯源"广播 action 列表供客户端重放。

**评估结论**：不采纳。理由：

1. **服务端权威 + version 短路已提供足够流畅性**
   - `server.js` 采用权威状态机（`Core.apply`/`Core.advance`），`makeView` 广播每个玩家视角。
   - `client.js` 已有 `if (view.version === lastV) return;` 版本短路，重复/过期状态包被直接丢弃，不做重复渲染。
   - `isProcessing` 互斥锁（500ms）已把玩家操作串行化，防止连点导致的竞态。

2. **乐观更新风险远大于收益**
   - 本游戏操作多为**成本结算**（买牌扣⊙、刷新递增、锁定保留），乐观更新需在客户端复制一份经济结算逻辑，等于维护第二份规则引擎。规则一旦演进（如新增技能、组合技），两端极易分叉——这正是当前架构极力避免的。
   - 服务端拒绝时回滚复杂度高：需记录被移动的卡、被扣的钱、市场补牌位置，回滚不干净会污染 UI 状态。

3. **事件溯源对当前规模是过度设计**
   - 单局 2~4 人、单次广播状态 < 几 KB，延迟主要来自玩家自身操作确认（< 100ms 本地服务器），无高延迟/丢包专项需求。
   - 若未来上线公网跨区域对战，可再评估"action 重放 + 状态快照"，届时以 `docs/` 中本决策为起点。

**替代措施（已实施）**：
- 客户端诊断日志黑匣子（`client.js` / `singleplayer.html` 的 `DIAG` + `diagOut`），渲染异常自动输出最近事件快照，替代"回滚"来定位同步问题。
- 服务端 `room.diag` 环形缓冲 + 局末摘要（AI 决策 + 卡牌埋点），定位状态推进异常。

## 程序化 BGM → **已否决并移除**（2026-08-11）

**原实现**：`FEATURES` 旁的程序化 WebAudio BGM（`bgmStart/bgmStop/bgmToggle/bgmMoodFor` 等，三档情绪循环）。

**评估结论**：整体移除，不保留开关。理由：

1. **程序化旋律在"背景音乐"场景效果差**：I-IV-V-vi 和弦循环 + 低音/琶音/hats 在长时间对局中单调刺耳，明显劣于精心编排的音频素材。
2. **游戏为静音优先的庭审主题**：连"审判"本身即强调严肃/安静氛围，无 BGM 比劣质 BGM 更贴合主题。
3. **音效（sfx）已独立保留**：操作反馈音效不受影响，`M` 键开关与 localStorage 记忆项一并删除。

**若未来要做**：改用预录音频素材（真 BGM），而非程序化合成；届时再评估音量/暂停/切换实现。

## 全部卡牌独特技能改造（2026-08-11）

**背景**：用户指出"很多卡牌只是换个名字的不同卡牌"——旧版 90 张选民牌中大量无技能或技能重复。

**方案（已实施）**：
1. **SKILLS 字典扩至 30 技能**：新增 11 个位置/议题系技能（见 repo 记忆"第十五批"列表），全部在 `doCount` 结算。
2. **90 张 VOTER_TEMPLATES 全量重写**：每张卡都有独立技能 + 技能参数（`tag/v/desc`），经脚本校验：无无技能卡、无重复"技能+标签"组合、30 种技能类型全覆盖。
3. **2p 死技能规避原则**：条件必须"2 人环内必可判定"——不写"相邻有本方牌"（2p 环邻位必为敌）、不写"比较双方亮出牌数"（永远相等），改用**半区/行首行尾/当前票数领先落后**等与座位数无关的条件。

**遗留说明**：AI 出牌仍为位置无关（按 `aiCardScore` 排序打第一张）——站位深度留给玩家，AI 通过 SK_VAL 估值与"政治操盘换敌方最高票卡"获得基础博弈力，暂不过度工程化。
